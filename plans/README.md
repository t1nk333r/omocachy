## MAJOR upstream discovery (2026-08-17, during plan 003 execution)

**Omarchy v4.0.0 (tagged 2026-08-14) removed `install.sh` entirely.** v4
installs via Arch packages (`omarchy`, `omarchy-settings`, `omarchy-keyring`)
applied by `omarchy-apply-system` as root from an ISO chroot, with
`OMARCHY_PATH=/usr/share/omarchy`. The old layout this project patches
(`install/preflight/`, `install/config/hardware/`, `config/uwsm/env`,
`install/config/walker-elephant.sh`) is gone from both v4.0.0 and master.
Consequences, all landed in plan 003: the installer pins its tested ref to
**v3.8.4** (last compatible stable tag, verified target-by-target), refuses
non-tested versions without explicit confirmation, and hard-aborts on any
tree lacking `install.sh`. **v4 support is a redesign, not a patch refresh**
— it belongs in the plan 011 investigation (whose scope now includes "should
this project become a v4 package-install wrapper?"). Note: my original audit
probes hit stale raw.githubusercontent.com CDN content; always verify
upstream facts via `git clone`/`git fetch`, not the raw CDN.

## Findings considered and rejected

- **Unconditional `/etc/sddm.conf` removal as a bug**: rejected — deliberate,
  tested decision from PR #28. Plan 006 may revisit it with evidence.
- **Prompting for username instead of `$USER`**: rejected — upstream Omarchy
  uses it as the git display name; the prompt is correct.
- **`sudo pacman -Syu` without `--noconfirm`**: rejected — interactive
  confirmation on a full upgrade is a feature in a watched installer.
- **`cp -r .` copying `.git` into `~/.local/share/omarchy`**: not a defect —
  Omarchy's updater needs the checkout; the real issue (updates clobbering
  patches) is plan 011.
- **`fetch-omarchy.sh` `exit 0` on the keep-existing branch**: not a bug —
  it runs as a child process, so `exit 0` correctly returns control to the
  installer; plan 004 only improves its messaging.
